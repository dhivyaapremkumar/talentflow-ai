# AI Usage Disclosure

This document is the YottaFlex-required narrative disclosure of AI usage and human
review for TalentFlow AI (brief §9: "Explain AI usage and human review"). Every claim
below is traceable to a specific entry in `claude_code_prompts.md` or
`chatgpt_prompts.md`; nothing is inferred, estimated, or assumed beyond what those logs
actually show, and nothing below describes review, testing, or usage that did not
happen.

**Status as of this writing:** Phases 1–10 implemented and pushed to GitHub
(`origin/main` at `ddd9a4e`); Phase 11 (final integration, verification, and
submission readiness) in progress. This document was first written during Phase 0
(architecture only) and left unedited through Phases 1–10 — a staleness gap
`docs/implementation_plan.md`'s Phase 11 row explicitly flagged, and which an earlier
Phase 11 editing pass only partly fixed (it left some meta-commentary about the old
draft that read as ambiguous). This is a full rewrite superseding every earlier
version; no prior draft of this file is authoritative.

## 1. AI tools used, and their actual roles

**Claude Code** (Anthropic) — used for essentially the entire project: all eight
architecture documents, the full database schema, the deterministic data generator,
the validation/detection engine, the service layer, the FastAPI backend, the React
frontend, every automated test, and this documentation pass. Evidenced by
`claude_code_prompts.md`, which has 44 logged entries (P001–P044). Model identity
reported by the tool across this session: Sonnet 5 (`claude-sonnet-5`).

**ChatGPT** — used only for early, pre-implementation project planning, per
`chatgpt_prompts.md` (P001–P005): initial project concept and architecture discussion,
a workflow-visualization request, and continued planning (P001–P003, each recorded as
a historical summary rather than a verbatim prompt, since the original conversation
text was not available to reconstruct exactly — the file says this explicitly for each
one rather than presenting a summary as an exact quote); then two later prompts about
the prompt-history process itself (P004–P005). **There is no evidence in
`chatgpt_prompts.md` of ChatGPT being used for code review, implementation guidance, or
any role after the architecture-planning stage** — this disclosure does not claim a
broader role than the log shows.

**No other AI coding tools** have been used, to the extent visible from this session.

## 5. Human understanding and verification limitations

Stated plainly, with no overstatement: **Claude Code wrote all the code and performed
all test execution, generation/validation/evaluation runs, live server verification,
and Playwright-driven browser checks described in this project.** The project owner
did not, to the extent visible from this session, personally run these commands or
exercise the application hands-on themselves. What the project owner did do, evidenced
directly in the prompt log, was review the *outputs* of that work — test pass/fail
counts, screenshots, live `curl` output, the P032 review's findings — and direct what
happened next at each boundary: approving, narrowing scope, correcting an approach, or
requiring a specific fix. That is a real form of review (§4), distinct from, and not a
substitute for, independently re-running the code oneself. If the project owner did
additional hands-on testing outside what is visible in this log, it is not claimed
here, since it cannot be verified from the log.

A related limitation: human review in this project has been of Claude Code's *outputs
and reports*, not independent line-by-line code review. Repeated, specific approval at
each boundary is a real correctness signal (§4), but it is not equivalent to a second
engineer independently re-deriving and re-checking the implementation.

## 6. Known limitations and remaining risks

- **Every numbered assumption (A-1…A-19) was an AI-proposed interpretation of an
  ambiguous requirement**, several corrected by the project owner before
  implementation began (§4) — AI output needed human direction at decision points
  throughout the project, not just at the start.
- **Self-consistency is not the same as correctness.** The generated data, the
  validation engine, and the detection layer agreeing with each other by construction
  (several deliberately share one implementation, per `architecture.md` §6) does not
  independently prove any of them match the brief's actual intent — only that they
  don't contradict each other.
- **Scope ambiguity recurred at nearly every phase boundary** (Phase 7 vs. 8, Phase 9's
  "Deliverables" row naming an API endpoint its own prompt never requested, Phase 10's
  assumption that a frozen API already existed). Each time, the resolution was to flag
  the gap explicitly and defer or ask, rather than silently expanding or silently
  skipping — a repeated pattern, not evidence the ambiguity stopped recurring with
  experience.
- **A dedicated review pass still found real defects after ten phases of per-phase
  self-testing** (P032's `DATABASE_PATH` blocker and the 422-error-shape
  inconsistency) — self-review by the same tool that wrote the code is not a
  substitute for an independent, differently-angled review pass.
- **A verified, unresolved dataset limitation**: the starter dataset's interviewer
  availability data ends 2026-05-20, which is before the real date this Phase 11
  verification was performed (2026-11-13). This means no interview can currently be
  scheduled against the committed starter dataset through the live API — confirmed
  directly (every one of 13 checked interviewers has zero slots after 2026-11-13; a
  live scheduling attempt against the latest known slot was genuinely rejected with
  `scheduled_start must be >= Application.screening_computed_at`). This is a property
  of when the fixed-seed dataset was generated relative to wall-clock time passing, not
  a code defect — the scheduling service's date checks are working exactly as designed.
  No availability data, system dates, or business rules were modified to work around
  it. It will recur for any further live demonstration of interview scheduling against
  this same starter database, and would need either a regenerated dataset with a later
  availability window or a live system actually run going forward from today.
- **No disparate-impact or legal fairness certification is made** for the screening
  formula (`business_rules.md` §8): excluding named protected-characteristic fields
  from the schema is a structural safeguard against those specific proxies, not a
  guarantee of fairness in any broader statistical or legal sense.
- **No automated frontend test framework** (vitest/React Testing Library or similar)
  exists; frontend verification relies on a successful production build plus
  Playwright-driven manual/scripted smoke checks, not a committed regression suite.
