## 3. How AI accelerated development

At this stage, the acceleration is specifically in the architecture/documentation
phase:
- Produced eight cross-referenced design documents, a directory structure, and 15
  explicitly stated assumptions (A-1 through A-15) in two drafting passes, rather than
  the project owner writing each document and consistency-checking the cross-
  references by hand.
- Surfaced concrete ambiguities in the original brief (e.g., whether "departments and
  required skills" meant skills belonged to the department or the requisition; how a
  duplicate application should be representable without violating a primary key) as
  explicit decisions for the owner to confirm or correct, rather than resolving them
  silently.
- When the owner's second round of decisions changed the data model (new entity, new
  ID scheme), AI tooling propagated the consequences across all eight documents in one
  pass (volume math, ID-format regexes, FK references, anomaly-count totals) rather
  than the owner having to track down every place a changed decision touched by hand.

This section does not claim a specific time saved (e.g., "N hours") — no such
measurement was taken, and claiming one without having measured it would itself be a
fabrication. It will be updated with concrete, verifiable detail (e.g., test pass
rates, generation runtime) once implementation begins.

## 6. Limitations of AI-generated suggestions

Observed and anticipated limitations, specific to this project:
- **Every numbered assumption (A-1…A-15) is an AI-proposed interpretation of an
  ambiguous requirement, not a verified fact.** Several were corrected or redirected
  by the project owner in P002 (e.g., A-2's screening-result design, A-4's actor
  model, A-10's duplicate-handling mechanism) — proof that the first pass's
  interpretation was not simply correct by default and needed human judgment to
  finalize.
- **AI-generated counts and formulas (funnel math, anomaly counts, the screening-score
  formula) are internally self-consistent by construction, but that is not the same as
  being empirically verified.** Self-consistency checking (cross-referencing numbers
  across documents) catches arithmetic and naming drift; it cannot catch a shared
  misunderstanding of what the brief actually intended, since the same (possibly
  wrong) assumption would be applied consistently everywhere.
- **AI can propagate a design decision across many documents quickly, which is a
  double-edged property** — a correction caught early (as in P002) is cheap to apply
  everywhere; an error not caught would also propagate everywhere just as fast.
- **No empirical/code-level verification has happened yet for anything in this
  disclosure**, because no code exists yet. Everything described as "verified" so far
  is document-level self-consistency, not runtime behavior.

## 7. How I verified correctness

To date (Phase 0, documentation only):
- **Self-consistency checks performed by Claude Code and described inline in the
  documents themselves** — e.g., `PROJECT_SPEC.md` §10 ("Consistency check performed")
  lists specific cross-document checks (ID-format regexes, lifecycle-state spelling,
  anomaly-type names, funnel-volume math, the `AnomalyLabel` row-count total). These
  are mechanical consistency checks, not independent verification that the design
  itself is correct.
- **Human review via a structured second pass**: the project owner read the Rev 1
  output and came back with specific, itemized corrections and confirmations (P002)
  rather than a general "looks good" — this is the primary correctness signal so far,
  since it reflects actual human judgment catching things the first pass got wrong
  (the duplicate-application ID conflict, the entity-count ambiguity) or wanted
  changed (`SystemActor`, screening explainability).
- **What has not yet happened**: no automated tests, no running code, no generated
  dataset to validate against, no checksum verification. These are the next
  verification steps, scheduled in `docs/implementation_plan.md` Phases 1–4, and this
  section will be updated with real results (test pass/fail counts, reconciliation
  output, checksum matches) once they occur — not before.
